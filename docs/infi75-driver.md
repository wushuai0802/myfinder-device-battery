# INFI75 Driver V1.2 电量路径静态分析

## 1. 结论摘要

- 现有证据不足以实现安全的只读电量读取器：未建立“当前电量”界面、请求命令、回复字段之间的完整链路。
- 已确认官方主通信封装是 `00` Report-ID 槽加 64 字节数据，共 65 字节 Feature；这不是已确认的电量协议。
- 有线 `05AC:024F / INFI75-1.1 / MI_03 / FF13:0001` 是与历史长度记录相符的候选，驱动实际按 Feature 长度筛选，未固定这个 usage 或接口。
- 已记录的 `2.4G Wireless Keyboard / FFB5:0001` 不满足产品名和 Feature 长度条件；没有证据证明此驱动经该接收器读取电量。
- 语言文件确有 `[MAIN.DIALOG] 20=当前电量 / Battery`，但 23 处该节名的直接代码引用均未取 id 20；不能从语言资源推出实际显示能力。
- 已定位的会话大量用于写按键、宏、灯光及屏幕；不得复制为电量查询的初始化。
- 最关键缺口是电量请求与解析、会话副作用和独立查询条件、带/无电量计固件的实际表现；本次不运行程序、不访问 HID、不改变支持状态。

## 2. 六个问题及证据

以下地址均为 `disasm/text.asm` 中的虚拟地址（VA），不是文件偏移。定义 `D[0..63]` 为调用者的 64 字节数据，`R[0..64]` 为传给 Windows HID API 的缓冲区；发送时 `R[0]=00`，`R[i+1]=D[i]`。所有索引均从零开始；不能把 `D` 与 `R` 的偏移混用。

“确认”仅指提供的静态文本或既有枚举记录；“推断”不代表固件语义或实际执行；“未确认”不以相似品牌补全。负面检索结论仅覆盖下述直接引用、调用点和已提供文件，不证明所有间接调用或未提供模块均无此功能。

### 2.1 设备匹配与集合

#### 产品配置与匹配链

`installed/device.xml:7–8` 列出两项：VID `05AC`、PID `024F`，产品名分别为 `INFI75`、`INFI75-1.1`，`identify="RKGK890"`、`type="1"`。没有 `2.4G Wireless Keyboard` 项，也没有 usage、接口或报告 ID 配置。

主程序 `0x451b80` 解析 `device.xml`：`0x451d0f` 选 `Singledevice.info`，`0x451e32–0x451ea0` 把 VID/PID 按十六进制转换，`0x451ecc–0x451f17` 取 `product_name`；`0x4520c3` 调 `0x456ee0` 注册匹配项。

枚举函数 `0x4586a0` 取得路径、HID attributes 和产品串：`0x4588d3` 调 `HidD_GetAttributes`，`0x4589da` 调 `HidD_GetProductString`，`0x458a02–0x458a19` 保存 VID、PID、VersionNumber。`0x457a97 -> 0x457e60` 比较注册项的 VID/PID；产品名非空时，`0x457f49–0x457f7b` 逐 UTF-16 字符比较，而非前缀或模糊匹配。`0x457130` 在枚举后的设备表中也用 VID/PID 和非空产品名精确选择，调用点 `0x450e33`。

`SONiX` 是 `local-enumeration-20261111.txt` 记录的厂商串；`0x457b73` 确实读取厂商串，但上述主匹配链未见以 `SONiX` 作为拒绝/接受条件。`RKGK890` 是 XML 的配置标识，不是已证实的 USB 产品串或协议签名。

#### HidP_GetCaps 字段与选择条件

| 路径 | 已核实的字段或条件 | 地址依据 |
| --- | --- | --- |
| 枚举元数据 | 读取 caps 的 `UsagePage`（偏移 `+2`）、`Usage`（`+0`），保存到枚举项；此处没有据此过滤 | `0x458935–0x458956` |
| 通信句柄 | caps 基址为 `[esp+0x10]`；保存 `OutputReportByteLength`（`+6`）到句柄对象 `+8`，`InputReportByteLength`（`+4`）到 `+0x0c`，`FeatureReportByteLength`（`+8`）到 `+0x10` | `0x458c17`、`0x458c71–0x458c87` |
| 主设备表 | 只把 `FeatureReportByteLength == 0x41` 的句柄放进主通信设备表；发送器按设备表索引取句柄 | `0x457b44–0x457b49`、`0x457bfc`、`0x457e00–0x457e43` |
| 另一个大包通道 | 主 Feature 条件不符时，检查 `OutputReportByteLength == 0x1001`，满足则保存为另一路句柄；不是 32 字节电量通道 | `0x457caa–0x457cbb` |
| 插入通知预检查 | caps 基址 `[esp+0x18]`，比较其 `+8` 即 Feature 长度 **大于等于** `0x41`；通过后重枚举，最终主表仍要求 **等于** 65 | `0x451382–0x45139a`、`0x4510d3–0x45110d` |
| 辅助 Input 通道 | 另一枚举器要求 caps 成功，并检查 `UsagePage == FFFF`、`Usage == 0001`；不是主 Feature 集合筛选器 | `0x448e90`、`0x449004–0x449023` |

上述主 Feature 路径没有硬编码 `FF13`、`FF68`、`FFB5` 或 `MI_03` 条件。枚举器在 `0x458a2a–0x458a66` 解析路径中的 `&mi_` 为接口号，但已定位的主句柄接受分支没有用该接口号筛选。不能把“读到了 usage/interface”写成“按该 usage/interface 选中”。

还需区分“临时打开检查”与“选为通信集合”：`0x4588b0` 在枚举阶段以访问权限 0 打开路径读取元数据；产品匹配后的 `0x458b20` 则在 `0x458bd2–0x458be8` 先以 `GENERIC_READ | GENERIC_WRITE`、共享读写及 overlapped 标志打开，随后才取 caps 和做上述长度筛选。因此不能声称官方只打开 `MI_03`，也不能把它的打开权限当作协议只读证明。

#### 与维护者既有枚举记录的对应

| 记录中的连接与集合 | 本次能作出的判断 |
| --- | --- |
| 有线 `INFI75-1.1 / MI_03 / FF13:0001`，历史 Feature 长度 65 | 符合已知产品名和主通道长度，是主 Feature 通道候选；未有完整的逐报告描述符，也未证明它是唯一满足者或它承载电量 |
| 有线 `MI_02 / FF68:0061` | 所给记录没有其 Feature/Output 长度；不能认定它会被拒绝，也不能把它认作 `0x1001` 大包通道 |
| 有线 `MI_01 col05 / FFFF:0001` | 与辅助 Input 枚举条件相符；已定位读取的是 4 字节事件，不是已确认的电量数据 |
| 接收器 `2.4G Wireless Keyboard / MI_02 col01 / FFB5:0001`，Input/Output 各 8、Feature 0 | 产品名不在 XML，且 Feature 0 不满足主通道的 65 字节条件；不得对其发送此 Feature 协议。记录本身还保留“可能是 INFI75 接收器，未确认” |

依据为 `local-enumeration-20261111.txt` 和 `engine/compatibility.json` 的 `infi75_observed`。后者仍为 D 级、`compatible=false`；本次没有实机复核，也不把候选集合提升为硬件支持。

### 2.2 电量交换：已知封装不等于已知电量命令

#### “当前电量”入口的核对结果

三个语言文件的第 13 行确有 id 20，但必须带节名解释：`[KB.DIALOG]` 也有 id 20，含义是“配置文件”，不能混用。

字符串表中 `MAIN.DIALOG` 位于 `0x570ed0`。检索 `text.asm` 全文得到 23 处 `push 0x570ed0`，对应语言 id 的集合为 `1,2,3,5,7,8,9,50,51,52,53,54`，没有 `20 (0x14)`。调用覆盖主界面文本创建/更新及系统设置提示，例如 `0x452627–0x4527c0`、`0x453092–0x453384`、`0x454213`、`0x45477d–0x45497f`、`0x454e2b–0x4550c4`。

`strings.txt` / `imports.txt` 中按 `battery / charge / gauge / 电量 / 電量` 检索未找到可接到电量解析的程序字符串或命名接口；`KeyboardLayout.xml` 的相同检索也无匹配。**这只说明尚未定位入口，不证明所有电量代码不存在。** `mui.dll` 实现、资源布局和固件升级程序不在给定分析文本里，无法排除间接构造 UI、资源驱动或未提供模块的行为。

#### 已确认的普通单包 Feature 交换

`0x457300` 的参数按调用点可还原为：`(D, length, device_index, delay_ms, want_reply)`。普通分支条件是 `length <= 0x41`；实际无论该值多小，都复制 64 字节并固定以 65 字节发送（`0x457369–0x4573b6`），所以这个长度参数不能用于推导 32 字节帧。

| 步骤 | 静态行为 | 地址依据 |
| --- | --- | --- |
| 发送前 | `Sleep(delay_ms)`；清零 65 字节本地缓冲区，四次 16 字节复制使 `R[1..64]=D[0..63]`，`R[0]=00` | `0x457372–0x4573b2` |
| Set Feature | `HidD_SetFeature(handle, R, 0x41)`；失败走错误处理并返回 | `0x457395–0x4573c2`；`0x45860e–0x45861b` 绑定函数指针 `0x597204` |
| 可选 Get Feature | `want_reply != 0` 时再 `Sleep(delay_ms)`，重新预填请求数据，然后调用 `0x458f20`，Get 长度取调用者的 `length`；常见调用传 `0x41` | `0x4573e9–0x45741d` |
| 一次协议重发 | 检查 **`R[4]`**：若为 `FF`，通过 `0x458ef0` 重发同一 65 字节 Feature，成功后再等待并 Get 一次 | `0x457425–0x45748f` |
| 应答判定 | 最后只以 `R[4] == 01` 标记成功；其他值不成功；没有把完整回复复制回调用者 `D` | `0x457492–0x45749e` 和普通分支的返回路径 |

这里 `R[4]` 等于去掉 Report-ID 槽后的 `D` 视角偏移 3，**不是 `R[0]`，也不是已证明的电量字节**。`FF` 是这个封装的一次重发条件，不是已知的“无电量计”值；`01` 是应答成功条件，不能解释为 1% 或充电。

Get 的实际实现是 `DeviceIoControl(handle, 0xB0192, R, length, R, length, ..., OVERLAPPED)`，随后 `GetOverlappedResult(..., TRUE)`（`0x458f20–0x458fae`）。程序确在 `0x458624–0x458631` 解析并保存 `HidD_GetFeature` 到 `0x597200`，但对这个指针的全文直接引用只找到赋值；上述路径并不直接调用它。

常见等待参数来自对象 `+0x850`，构造时设为 `0x0a` 即 10 ms（`0x413fe4`）；也有明确传 5 ms 的灯光路径（`0x427d50–0x427d63`）。**Sleep 是前后间隔，不是 I/O 超时。** `0x458f93` 等待完成没有静态可证明的墙钟超时；`0x457300` 也没有检查 Get 的返回字节数后再判 `R[4]`。不能据此声称查询在 10/20/30 ms 内必定结束。

普通单包分支最多初次 Set 一次加 `R[4]==FF` 后重发一次、相应 Get 最多两次。`length > 65` 的另一分支把长度右移 6 按 64 字节分包，并有 Set 失败后的最多十次额外重试（`0x4574a3–0x45757e`）；这是批量写路径，不能冒充电量查询重试策略。

发送封装没有添加校验和或 CRC。调用者的部分数据块带字常量 `0x55AA`，在 x86 小端内存中对应 **`AA 55`**；例如 `0x436e6f` 写在 `D[62..63]`。它是已见固定尾标，未证明是校验，不应倒写成已证实的 `55 AA` 线序。

#### 完整请求能恢复到什么程度

以下两帧在 `0x41682d–0x416847`、`0x416abb–0x416ad5` 可逐字节恢复，括号是明确的零填充区，不是省略未知字节：

```text
R[0..64] = 00 04 18 [00 × 62]
R[0..64] = 00 04 02 [00 × 62]
```

这是按键写配置事务的边界帧，**两者均不是已确认的电量请求，也不是建议发送的握手**。本次未找到可以标为电量命令的完整帧。

| 电量必需信息 | 结论 |
| --- | --- |
| 电量命令、完整 Set/Get 请求、是否仅 Get 即可 | 未确认 |
| 电量报告类型、Report ID、总长度 | 未确认；上述 Feature `00/65` 仅为已定位通用通道 |
| 回复电量偏移、有效范围及单位 | 未确认；不能默认 `0..100`、百分比、档位或电压 |
| 充电/满电/外接电源标志 | 未确认 |
| 无效值、休眠值、无电量计值 | 未确认；不得套用 `00`、`FF`、`FFFF` 等哨兵 |
| 电量校验、命令回显和回复关联规则 | 未确认；封装不算校验不等于固件协议无需校验 |

由于没有电量入口，**无法列出“读电量之前必经”的命令序列**，也没有证据证明绕过会话、只发一条命令能得到电量。下面列的是已定位事务，不是电量前置条件；“会话开始/结束”只是基于发送位置的推断名称。

| 命令或操作（`D` 视角） | 代码作用与副作用判断 | 依据 |
| --- | --- | --- |
| `04 18` | 常在写事务前出现；是否握手、进入配置模式及其独立副作用未确认，不能认定只读 | `0x41682d–0x416847`、`0x436d1d–0x436d37` |
| `04 11`，`D[8]=09` | 后续构造按键映射，发送批量数据和尾标；属于写配置流程，不能作电量请求 | `0x416857–0x41686a`、`0x4168dc`、`0x416a83–0x416aa6` |

| `04 13`，`D[8]=01`，然后参数块 | 把本地配置记录取到参数块，附尾标后 Set，无完整配置回读；属于配置/灯效参数写入，不是读配置 | `0x42d340`、`0x42d3a5–0x42d449`；`0x42d870–0x42d967` 有另一参数块 |

| `04 F5`，`D[8]=03/09` | 唯一定位到调用者缓冲区回填的 Feature 候选；调用后按键索引解析 RGB/灰度并更新 `KEY_INFO+0x30`，不是已确认电量 | `0x42da85–0x42dab1`、`0x42dad5–0x42dbaf`；封装 `0x457770` 有异常分支，见第 4 节 |

初始化不是天然纯查询：`0x414897–0x41496f` 向任务队列加入 `1,2,3,4`；调度器任务 4 在 `0x4375ab / 0x4375b3` 调用两套映射写函数。实际是否成功执行依赖运行状态，但静态上已经存在打开设置后进入写配置的路径。因此不得为了“让电量可读”复刻整个官方初始化。

`0x457a30` 的已核实设备发现步骤只读路径、attributes、产品/厂商串与 caps，没有在该发现函数里看到电量命令或固件版本 Feature 请求。电量是否还需要额外握手、进入模式、读取固件/配置，仍未确认。

### 2.4 触发条件：未确认电量轮询或页面触发

确认有以下调度行为，但均不能标为电量轮询：

- `0x414982–0x414990` 设置定时器 id `0xC8`、间隔 `1000 ms`。`0x414a20–0x414a3c` 首次回调即 `KillTimer(0xC8)`，再做 `0x414a50` 的版本/升级提示检查。这是延迟一次处理，不能写成每秒读电量。
- 主界面 `0x4543d0` 对 id `0x64` 调 `0x451460`（图片轮换），对 id `0xC8` 调 `0x4515a0`（取消定时器并读取 XML 的 `upgrade.url` 等），也不是已确认电量请求。
- `0x437440` 消费配置任务；队列为空时，`0x4376d2–0x437725` 按页面/模式值转到 `04 F5` 的灯色回读、其他灯光处理或自定义灯色写入。不是电量页面证据。

所以“打开哪个页面读电量”“多少秒刷新一次”“是否仅接线/接收器也可读”均未确认。已记录接收器不满足这条主 Feature 路径，仅排除对它套用此路径，不证明所有固件、其他通道或其他官方软件都不能读。

### 2.5 固件差异与无电量计固件

`local-enumeration-20261111.txt` 记录安装目录存在文件名带 `V1.27…带电量计`、`V1.30…无电量计` 的两个升级程序，但文件未复制。本次没有读取、运行或分析它们；文件名不能证明当前键盘刷入哪一个，也不能推出无电量计时回复全零、固定 100%、`FF`、电压或估算值。

确实找到版本相关分支，但用途是升级，不是显示电量：

1. `0x458a14–0x458a19` 把 `HIDD_ATTRIBUTES.VersionNumber` 保存到枚举项；`0x457c89–0x457c93` 转存到设备记录 `+0x220`，`0x4579c0–0x457a17` 仅取出这个缓存字段。没有在这个 getter 中发 HID 请求。因此它不是已证实的“读键盘固件”命令，接收器的同字段也不等于键盘固件版本。
2. `0x414b09–0x414b6e` 比较产品名 `INFI75-1.1`，对该产品使用字符串 `0127`（`strings.txt` 地址 `0x56e61c`），经过字符串到整数转换后决定是否提示升级；`0x4354a0–0x435508` 有同类升级判断。
3. 字符串 `0x56e6d8` 包含 `_HFD80CP100_V1.30_20230620(INFI75)`，后续升级路径还用产品名选择升级文件（`0x4355df–0x43562d`），最终 `CreateProcessW`。不能把这个文件名分支解释成电量计能力判断。

**未找到可以连接到 id 20 或电量解析的版本/能力标志判断。** 参数 `+0x83e` 在已定位路径中控制 RGB 与单值颜色处理（如 `0x42db59–0x42dbaf`），没有依据把它命名为“有电量计”。无电量计固件的回复与 UI 表现均未确认。

### 2.6 与 #532 的关系（仅记录）

任务简报给出的 KEYVERSE INFI100 抓包是 `FF60:0061` 上 `20 01 00…00 21 -> 20 01 00 53`；本工作树给定 INFI75 证据中没有这份原始抓包，本节仅引用简报背景，不作独立复核或跨型号推导。

本次检查 `0x457300 / 0x457590 / 0x4576b0 / 0x457770` 及其直接调用点，没有定位到作为 HID 请求头的 `20 01`，也没有定位到 32 字节电量帧。已见普通 Feature 为 `00 + 64` 字节、大包 Output 为 `00 + 4096` 字节，辅助 Input 按 4 字节读取；不能仅凭出现常量 `0x20` 推导 32 字节协议。

具体易混点：`0x427d36`、`0x435b33` 的字常量 `0x2004` 是小端 **`04 20`**，且用于写灯光；`0x416d1b`、`0x4173cd` 的 `0x0201` 位于按键映射数据内部，是 **`01 02`**，并非请求头 `20 01`。没有证据证明 INFI75 使用 #532 的协议；上述有限检索也不证明程序不能用其他方式动态构造它。
