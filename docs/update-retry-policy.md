# 更新请求退避策略

程序更新检查与附件下载使用相互独立的等待状态。自动检查仍在启动两分钟后开始，并保持六小时周期；手动检查只绕过这个普通周期，仍遵守目录（catalog）服务端等待。已缓存、当前频道和跳过判断仍有效的官方签名附件不因 catalog 等待而被阻止；附件（asset）403/429 只限制附件请求，避免重复访问 CDN。

收到有效 `Retry-After` 秒数或 RFC 1123/R 格式、以 GMT 表示的 HTTP-date 时，等待到该时间；`X-RateLimit-Remaining: 0` 配合有效 UTC epoch `X-RateLimit-Reset` 时也等待到 reset。多个有效期限取最晚值，绝不为缩短体验而提前请求。负数、溢出、非 HTTP-date 的日期文本、过去日期和非法值均视为无可靠提示，使用本地退避：连续限流失败从 5 分钟起按 5/10/20/40 分钟增长，随后封顶 1 小时；成功的同一通道会清除其等待和失败计数。程序不在一次调用内循环重试。

旧 `update-state.json` 的 `NotBeforeUtc` 来源和作用域未知，升级后仍作为 catalog 与 asset 的保守共同门禁，不会被截短到一小时或无条件清零。新状态分别记录 catalog/asset 的期限、失败次数和来源（服务端或本地退避）；跳过、已见、已通知版本及缓存发行版继续保留。坏 JSON 仍按既有保护路径处理。

界面分别显示检查中、缓存版本、本地剩余等待、刚收到明确服务端限流，以及无法归类的 403 访问拒绝；本地等待不会伪装成新的网络错误。验证仅使用假 HTTP、注入时钟和临时状态文件，覆盖 Retry-After 秒数/日期、reset、组合期限、非法提示、指数退避、成功复位、手动/自动门禁、catalog/asset 隔离、旧状态迁移和缓存 UI 语义。未验证 GitHub 自身限流、真实 CDN、真实安装或旧安装自动获得修复。
